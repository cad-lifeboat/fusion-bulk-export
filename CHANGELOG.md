# Changelog

## 0.3.5

- **Every export now says which designs are assemblies with designs inserted from other designs.** Their `.f3d` holds only links to those designs, so another program opening that one file sees just the assembly's own bodies. The summary (results window, `export` and `status` on the command line) says, with the count only: "3 assemblies use designs inserted from other designs. Their .f3d holds only links to them; the full geometry is in their .step, and every inserted design is in this folder too. To build an .f3z beside each, run the export again with "Also build .f3z for assemblies" ticked, or: python3 scripts/autorun.py bundle <folder>." (when some inserted designs are not in the export, it says how many; without STEP files it does not mention them). It counts every design in the folder whose newest exported version inserts at least one other design, each once, including designs already up to date from earlier runs, and it works from the `references` already recorded in `manifest.json`, so folders from earlier versions need no new export. `index.html` has a new section **Assemblies with inserted designs** naming each one with a link to its folder and files and, for each inserted design, a link to its exported `.f3d` (or "not in this export"); `index.csv` has a new `inserted_designs` column (the inserted designs' `.f3d` paths, separated by "; "); `export.log` has one line per assembly with its name and how many designs are inserted into it; `check` prints the count as a note, never as a problem.
- **Optional: an .f3z beside each assembly, built from the exported files.** A new box **Also build .f3z for assemblies** (off by default, remembered; note "A single file with its inserted designs, beside the .f3d."), `--f3z` on `export` (job key `"f3z_bundles"`), and a new command `python3 scripts/autorun.py bundle <folder>` for a folder already exported (no Fusion; `--older-versions move|keep|delete`). Each assembly gets `<assembly> v<N>.f3z` beside its `.f3d`: an .f3z-style bundle (a Deflate zip laid out as Fusion's own: `Manifest.json`, one UUID-named `.f3d` per distinct design, `DesignDescription.json` with the link graph and each design's lineage and version URNs) holding the assembly's `.f3d` and those of the designs inserted into it, nested ones too, each copied byte for byte. The `.f3d` files Fusion wrote are never changed, moved or replaced. It is not Fusion's own File > Export `.f3z` (that one re-saves each design and may differ). Inserted designs are matched by cloud id and the version the assembly uses: each link in `references` now records its `version`. The links' neutronRole is read from the assembly's `Manifest.dat` when the Python building it reads Zstandard (3.14 or newer; not Fusion's own), else left out and added by a later `bundle` on such a Python. Not built, with the reason in the report, when an inserted design (that version) is not in the export, a `.f3d` changed since it was exported, links are out of date with no versions recorded, or another file has the name. Recorded on the assembly's entry as `f3z` (role `f3z_bundle`, path, size, SHA-256, members) or `f3z_not_built`; rebuilt when one of its designs changes, the previous one following **Older versions of a design** (`f3z_older`); one changed since it was built is never written over; an assembly's older version moved or deleted takes its `.f3z` along. The assemblies note now ends "To build an .f3z beside each, run the export again with "Also build .f3z for assemblies" ticked, or: python3 scripts/autorun.py bundle <folder>." or, once built, "Built 3 .f3z files beside them." and "1 could not be built; the report says why."; `index.html` links each `.f3z` (F3Z) beside its assembly, `index.csv` has a new last column `f3z`, `check` checks each one, and `status` shows the last run's `.f3z` counts. The dialog's first size is 800 high (was 740).
- A folder exported by an earlier version records which version of each inserted design an assembly uses on its next export, for assemblies already up to date too (read from Fusion's file list, nothing is opened or exported again), so an `.f3z` can then be built for every assembly.

## 0.3.4

- **CAM tool libraries are exported too.** Each of your own tool libraries (Manufacture > Tool Library: Local, cloud, hub and external ones; Autodesk's sample libraries are skipped) is saved once per export, at its start, before any design, as `Tool libraries/<location>/<folders>/<library>.json`, the library as Fusion hands it to add-ins (`ToolLibrary.toJson()`), ready to import in Fusion again (Tool Library > right-click a library folder > Import). The dialog has a new box **Tool libraries** (on by default, remembered) with the note "Your CAM tool libraries, one .json file each."; the command line has `--no-tool-libraries` and `--tool-libraries-only` (only the libraries, no designs: quick); a job takes `"tool_libraries": true | false | "only"`. Unchanged libraries are "up to date" and not written again; a changed one replaces its file and its previous copy follows **Older versions of a design** (moved to `Older versions/Tool libraries/...` as `Mills (2026-11-20).json`, kept beside under that name, or deleted), only while that copy is unchanged since export. A library gone from Fusion keeps its file. `manifest.json` has a new top-level `tool_libraries` list (location, URL scheme only, path, tool count, bytes, SHA-256, export date, status and error); the summary says "Exported 3 tool libraries (412 tools).", `index.html` has a Tool libraries section, `index.csv` a `tool_library` row each (new `location` and `tools` columns), and `status` and `check` cover them (`check` verifies size and SHA-256; a missing file is a problem). A Fusion without the CAM API, or one that fails reading the libraries, gives a warning in the summary; the designs are exported all the same. Nothing in Fusion is ever changed. A hub named "Tool libraries" gets a "~1a2b" suffix on its folder. The dialog's first size is 740 high (was 700) for the new row and its note.

## 0.3.3

- **Behaviour change for re-runs: older versions are now moved into an `Older versions` folder by default.** When a design got a new version since the last export, re-exporting used to leave the old version's files beside the new ones (`v3` beside `v4`). Now, once the newest version is saved and checked (complete, no STEP failure), the files this export recorded for the older versions are moved (not copied) into `Older versions` at the top of the export folder, under the same folder path; a name already taken there gets " (2)", " (3)"… before its extension. This also happens on a run where the newest is already up to date, so the first re-run tidies an existing folder. The new dialog choice **Older versions of a design** (remembered; `--older-versions move|keep|delete`; `"older_versions"` in a job) offers **Move to the Older versions folder** (the default), **Keep beside the newest** (the old behaviour) and **Delete**. Nothing the export saved is ever deleted unless you pick Delete. Only files `manifest.json` lists for an older version of the same design, inside the folder and unchanged since export (size and SHA-256), are moved or deleted; a changed one keeps its version where it is ("kept: changed since it was exported"), and files you added yourself are never touched. Older versions stay in the manifest as `"status": "moved"` (with `moved_files`, each with `moved_to`) or `"status": "removed"`, with the date; the summary says "Moved N older versions (M files) to Older versions." or "Deleted N older versions (M files).", `index.html` lists them under collapsed sections, `index.csv` has `moved` and `removed` rows, `status` counts them and `check` does not count them as problems. Later exports, `check`, the report and the link map never look inside `Older versions`; links (`references[].path`) point at the linked design's newest exported `.f3d`. A hub named "Older versions" gets a "~1a2b" suffix on its folder.
- Designs the export opens are closed again afterwards in every case, so a long run no longer leaves some of them open in Fusion (a linked design opened under another version than one already open, one Fusion opened a moment late, or one it showed instead of keeping hidden). Documents that were open before the export are never closed. `export.log` and `manifest.json` record how many documents were open at the start and end of a run.
- STEP files include hidden bodies and hidden components when Fusion allows it: the add-in sets the STEP export's `isIncludingInvisibleBodies` and `isIncludingInvisibleComponents` when that Fusion has them (only the export options change; nothing in the design is shown or hidden). Each design's manifest entry records `step_includes_hidden` (`true`; `false` when this Fusion has neither; `null` when only one exists or setting failed, with `step_hidden_error`). In a real run, 24 of 491 designs had an empty STEP only because all their bodies were hidden.
- The STEP check compares against the right number: every distinct solid body of the design when hidden bodies were included ("STEP has 40 solids, fewer than the 96 distinct ones in the design"), else the visible ones as before. The tolerance is unchanged.
- A design with no solid bodies at all (sketches, surfaces or meshes only) is no longer a warning: its empty STEP is expected. Its row in `index.html` and `index.csv` (new `note` column) has the note "No solid bodies (sketches only): its STEP is empty." (or "surfaces only", "meshes only"), the warnings count in the results window, `index.html` and `status` leaves it out, and `check` does not flag it (`no_solid_bodies` in its counts). The manifest records `step_note`, and `surface_bodies` and `mesh_bodies` for such designs.
- When Fusion cannot include hidden bodies, the warning says so in plain words: "Its STEP leaves out 3 hidden bodies; they are in the .f3d." or, when that leaves the STEP empty, "All its 3 bodies are hidden, so its STEP is empty; they are in the .f3d." The summary, `index.html` and `status` add one note when that happened ("2 designs have a STEP file without their hidden bodies: ..."); `check` prints it as a NOTE (`hidden_left_out`), never a problem, also with `--strict`.
- Folders exported by earlier versions read the same way: their recorded STEP warnings are worked out again from the recorded counts, so sketch-only designs stop counting as warnings without exporting again.
- Counts of solids read as plain English ("STEP has 1 solid, ...").

## 0.3.2

- The STEP file is an option, on by default: the dialog's "Also save a STEP file for each design" (remembered; unticked, a note says "Without STEP you get only .f3d files, which open only in Fusion."), `--no-step` on the command line, `"step": false` in a job. Without it each design is saved as `.f3d` only; its manifest entry records `"step": "off"`, `index.html` and `index.csv` show "STEP not requested", the summary, report and `status` say "STEP files were not requested for this export.", and `check` treats it as intended. Exporting into the same folder with STEP on again adds every missing STEP (those designs are exported again); with it off, a folder that has STEP files keeps them and nothing is exported again.
- A STEP that Fusion cannot write no longer throws the design away: its `.f3d` is kept, with the warning "Saved, but Fusion could not write its STEP file" (counted under warnings, `"step": "failed"` with the reason in the manifest), and the next export tries the STEP again. Before, the design counted as failed and its `.f3d` was discarded (or, for an incomplete STEP, left on disk unrecorded).
- `manifest.json` maps every link to its exported file: each of a design's `references` has the `path` of that linked design's exported `.f3d` in the folder (null when it is not exported there), filled in at the end of every run, so a design exported after the assembly that links to it is found too. Each file of an entry has a `role` (`archive`, `step`; the thumbnail `thumbnail`). Older folders are read as before.
- README: "Why is my assembly's .f3d almost empty?" in Questions (the assembly's `.f3d` holds its own bodies and its links; each linked design has its own `.f3d` in the export, and the assembly's `.step` has the full geometry).
- The low-memory note no longer shows on nearly every export on an 8 GB Mac: macOS's everyday "warning" memory pressure no longer counts, only a lasting "critical" one (the memory stop rule is unchanged).
- The dialog no longer makes Fusion log "maximumHeight: 3 : invalid argument value" twice each time it opens (the tree's "no maximum" is now given only when the tree is made; its height is unchanged).
- Command line: a job rejected at once (an output folder Fusion cannot use) prints just the one rejection line ("Waiting for ..." appears only after 5 s), and an empty output folder the command had just created for it is removed again. `--restart-fusion`'s help is one short sentence.
- README: a short Questions section (Linux, exporting by hand).
- Long runs: when Fusion itself uses too much memory, the export stops itself cleanly ("Stopped: Fusion is using a lot of memory"; close Fusion, open it again and export to the same folder to carry on). It judges Fusion's own memory, not how full the computer is: it stops only when Fusion holds over 70% of the computer's memory, or has grown by over 4 GB in the run while the computer is under memory pressure (macOS's own pressure level; on Windows, little commit and physical memory left), and only when that holds for 5 designs in a row over at least 30 seconds, never before the 25th item and never while Fusion holds under 2 GB. When other programs use up the memory, it goes on, and only when the computer stays critically short of memory for a while (macOS's critical pressure level, not the warning level an 8 GB Mac reports almost all the time with Fusion open; on Windows, little commit and physical memory left) do the report, the results window and `status` say "This computer was low on memory during the export; closing other programs may speed it up." Switch it off with `FUSION_BULK_EXPORT_MEMORY_GUARD=off` or `"memory_guard": false` in `settings.json`.
- The report (`index.html`) and `status` show how much memory Fusion used ("Fusion memory: 1.4 GB ..."; in `status`, over every run into the folder); `export.log` and `autorun-result.json` record it over the run (a line at design 25, then every 100).
- The add-in lets go of everything of Fusion's after each design, also after a failed one, and runs Python's garbage collector after each item.
- Command line: `export --restart-fusion` (opt-in) finishes a long job by itself: after a memory stop it quits Fusion politely (only when nothing but an empty "Untitled" is open in it), opens it again and carries on; after a crash it opens Fusion again. At most `--max-restarts` times (20), never more than once per 50 designs (a memory stop sooner than that ends the command with 75 and one line saying a restart would not help); `--restart-fusion=force` also ends a Fusion that will not quit within 60 s.
- Counts read as plain English everywhere: "1 design", "8 designs", never "design(s)" (results window, message box, report, `status`, `check`, progress, the tree's "chosen" line, inventory log lines).
- Drawings and electronics are explained without jargon: "Drawing not exported: Fusion's drawing export crashes when an add-in runs it." with "To keep a copy, open the drawing in Fusion and use File > Export (PDF)."; "Electronics file (.fbrd) not exported: Fusion offers no export for it to add-ins."; the summary says "7 files can't be exported by an add-in (drawings, electronics). They are not failures; the report lists them."
- Network drives: an output folder on a mapped drive (such as `X:\Backups`) keeps its drive letter everywhere; the summary's "Report:" path used to show the `\\server\share` path behind it. Output folders given as a network path (`\\server\share\...`) work too: Fusion writes to the computer's temporary folder and each file is then copied into place whole.
- The results window now shows after long runs: it used to be replaced by a plain message box when Fusion took more than 5 seconds to open it (seen after a two-hour run). The add-in now waits while Fusion is busy and shows the box only when Fusion has been free for a while and still has not opened the window; the box now also says that nothing is lost.
- Command line: exit status 75 when the export stopped for memory, 76 when a restarted Fusion did not start the add-in, 77 when Fusion closed or crashed during the export (it used to wait until its time-out); `export --help` lists them all.
- Command line: a job whose output folder Fusion cannot reach or create (a network drive connected only in the terminal's session) is answered at once with one line and exit status 1; it used to be taken silently while the command waited up to 24 hours. If Fusion takes a job and no result appears within 60 s while it is idle, the command stops with a plain line.
- Command line: the installed add-in is judged by its files, not its install stamp, and the line says so plainly ("installed copy differs from this checkout; kept the installed one; run scripts/install.py to replace it"); the same files under an old version label are named as such. The Windows installer now copies every file (it kept an old manifest whose size had not changed).
- CI: the macOS test jobs run on pinned images (macos-15, and macos-15-intel for Python 3.9) instead of the queue-starved macos-latest.

## 0.3.0

Tested on real Fusion 2706.1.17 on macOS and Windows 11 before release: the dialog and tree, small and whole-account exports (59 designs), resume from a folder made by 0.2, cancel and continue, long output paths, the results dialog and the command line. Not yet exercised on real Fusion: runs of hundreds of designs with this version, the pause after repeated failures, and a design whose links Fusion cannot read (covered by automated tests only).

### What you get
- Readable names: files and folders keep their real names, in any language, with only the characters Windows or macOS cannot store replaced. Designs are saved as `<name> v<version>.f3d` and `.step`. A short `~1a2b` suffix is added only when two items in one folder would get the same name, and same-named sibling folders stay apart.
- Export folders made by earlier versions keep working: what is already there keeps its short name and is not exported again; new items go in readable folders beside them, and the report says so ("Older exports keep their old folder names; new items go in readable folders").
- Other files are saved too: PDFs, images and uploaded files as they are, under their own names.
- Drawings and electronics are **not supported**: exporting a drawing's PDF through Fusion's API crashed Fusion itself in testing (on Windows and macOS), so drawings are never opened. They are listed with "Fusion cannot export drawings safely through its API (use File > Export in Fusion)"; electronics and other Fusion-only types with the reason the API cannot export them. Both count as "N not supported by Fusion's export (electronics, drawings)": a neutral line of their own in the summary, `index.html`, `index.csv` (status `unsupported`) and `status`, apart from failures and from what you chose to skip.
- Linked designs: when a design with links fails, the reason reads "A linked design is missing or cannot be opened (N links)" instead of Fusion's raw error, which is kept beside it in the report. Designs whose links point to older versions are exported as they are and noted (not a failure) in the summary, `index.html`, `index.csv` and `status`. `inventory.json` marks designs with links and out-of-date links. When Fusion cannot read a design's links at all (it answers with an error), the design is still exported, with a warning: "Links to other designs could not be read; the design itself was exported". Before, such a design failed at once on both tries.
- On Windows, names are cut at 64 characters so typical layouts stay under 260-character paths; a file whose full path is still longer is saved, and the summary and `index.html` say how many there are (Explorer may not open them; a shorter output folder avoids it). The output folder itself may be at most 200 characters on Windows: a longer one is refused with that reason in the dialog and on the command line.
- Each design's thumbnail is saved beside it as `<name> v<version>.png`.
- Exported files carry the design's modified date.
- A report in the output folder: `index.html` lists every item with its status and links to its files, failures first with the reason and what to do; `index.csv` has the same as a table.
- Separate counts: exported now, already up to date (designs), other files saved, other files already up to date, skipped, not supported, failed. A re-run no longer looks as if nothing happened.
- Each STEP is checked as it is written: a broken file is tried again, and a STEP with no bodies, or fewer solids than the distinct bodies Fusion showed, is exported with a warning, shown at the end and in the report. Other differences in the count (a STEP may write a part used twice once or twice) are only recorded.
- Slow items: an item Fusion takes more than a minute on (a design locked in another team can block it for minutes) is listed under "Slow items" in `index.html` (`slow_seconds` in `index.csv`), and the summary says how many. A design whose failed attempt took more than two minutes is not tried a second time in that run.

### The dialog
- Shows the version that is running.
- **Save to** row with **Browse…**, remembered between runs (first suggestion: `Documents/FusionExport`). The line under it says when the folder already holds an export ("Continues the export in this folder").
- **Also save other files (PDFs, uploads)**, on by default and remembered.
- The tree: a filter box for project names, keyboard use (arrows, Space, Enter), a file count beside each opened project or folder, projects already in the chosen folder marked as exported, a loading row while a folder opens, and an error with **Retry** when a folder cannot be listed instead of a silent "No folders".
- The progress bar moves within a project, and the text shows the time so far, the average time per design and how many failed. Other files show as "file N". The item is named before Fusion starts on it, so a stall shows where (`export.log` gets an "exporting" line first too).
- The export dialog: the tree spans the whole width of the dialog and comes last, after **Save to**, the other-files box and the **Export** choice, so every control is in view at first (the dialog opens 520 x 600, which fits a screen 1080 points high); its height is set explicitly and no longer depends on what the page shows (a test build showed it as a thin strip on macOS); its scrollbars follow the light or dark theme. Long names end in "…" with the full name on hover; **Save to** and **Browse…** sit on one row, with the folder below (a very long path is shortened in the middle, the full path on hover).
- A results dialog at the end, with **Open report** and **Open folder** on its page and one **Close** button: a one-line headline (Finished, Cancelled, or Stopped with the reason), the counts with zero rows left out, up to three failures by name with "and N more in the report", "Run again to retry the N failed" when something failed, notes (not supported files, slow items, low disk space, long Windows paths) and the output folder. The page is written with the results already in it, so it never waits for Fusion to pass them on; if a button gets no answer within 2 seconds, the page shows the path with **Copy**. Only if Fusion cannot open the dialog at all does the same summary come in a message with OK, and `results-fallback.log` beside the add-in says why.
- Expected problems (a folder that cannot be used, a damaged manifest, a full disk, Fusion signed out) are explained in a sentence or two with what to do. Anything unexpected is saved to `errors.log` beside the add-in, and the dialog shows the details ready to copy into an issue. Those details leave out paths and project and design names.
- On a Fusion too old for the tree, the dialog still opens and offers Everything.

### Reliability on big accounts
- The export stops itself after 5 designs fail in a row (offline or signed out) or when the disk is full or the output folder is gone, instead of failing everything that is left. From the button it pauses with the reason and the last error and asks "Try again now?" (OK carries on, Cancel stops).
- One export at a time per output folder: `export.lock` is held while a run uses it, and a second export into the same folder (another Fusion, or a command-line job) is told "Another export is using this folder".
- Warns when less than 1 GB is free, and keeps the computer awake while it runs.
- Designs that an assembly opens alongside it are closed again afterwards, so a long run no longer fills Fusion with open documents. Designs you had open, and new unsaved documents, are never touched.
- After a crash of Fusion mid-export, the next run clears the stale `export.lock` (its process is gone) and the half-written `.staging` by itself.
- Finished items are recorded in a small journal file, and the manifest is rewritten only every 50 items or 30 seconds, instead of after every design.
- Resuming compares each file's size and modified time instead of reading every file again.
- No limit on how deep folders go (on Windows the output folder's own path may be at most 200 characters). Fusion writes to a short temporary path first and the add-in moves the file into place, because Fusion stops responding when handed a very long path on Windows.

### Command line
- `autorun.py check OUT` checks every exported file again without Fusion; `verify-export.py` now runs the same checks.
- `--designs-only` leaves out the other files. `--drawings` is still accepted for one release but does nothing: it prints one line saying drawing export was removed because it can crash Fusion.
- `--limit N` stops after exporting N designs in this run; designs already up to date and other files do not count, and the other files of every folder visited up to then (the rest of the folder where the limit was reached included) are still saved.
- `--folder PROJECT_ID:id=FOLDER_ID` chooses a folder by its id (listed in `inventory.json`), which also works for names with `/` in them.
- `status` prints the new counts, when a run stopped itself and why, low disk space, link problems and out-of-date links, and includes items still only in the journal.
- Stopping the command (Ctrl-C) or a timeout before Fusion started the job withdraws the job, and the command says so in one line (no traceback), so Fusion does not run it later by itself. An output folder that cannot be created is one plain line too.
- The toolbar button and command-line jobs work side by side: the button stays after a command-line export, and a job sent while someone exports with the button gets a "busy" answer instead of waiting. The answer is written beside the add-in, never into the running export's folder.
- The command installs the add-in from its checkout only when none is installed or the installed one is older by version: it never downgrades, keeps one of the same version, replaces nothing while an export runs, and says in one line which add-in it used.
- The command no longer edits the add-in's settings to make Fusion start it: if the add-in is not running, it says how to switch it on.
- `reset` is no longer needed; it only clears job files left by an earlier version.

### Install
- macOS: `Install (macOS).command` is not signed; the first time, right-click it and choose Open (or System Settings → Privacy & Security → Open Anyway). The README and the download's `README.txt` say so.
- The download is one folder, `FusionBulkExport-<version>`, with `Install (macOS).command`, `Install (Windows).bat` and a `README.txt`. The installers copy the add-in into Fusion's add-ins folder, so the green "+" step is no longer needed: switch it on in Fusion and tick Run on Startup.
- `scripts/install.py` does the same from a download of the repository (`--uninstall` removes it).
- Every installation carries `install-stamp.json` (its version and a hash of its files); `install.py`, both zip installers and the command line put the same one in place.

### Under the hood
- Removed a developer test from the add-in that could upload files: nothing in the download can upload, save or delete anything in your account, and a test checks the zip for it.
- Tests run on macOS, Windows and Linux for every change, with a privacy scan.
- `scripts/release.py prepare X.Y.Z` sets the version, moves these notes under it, runs the tests and builds the zip.
- `SECURITY.md` and `CONTRIBUTING.md`; the bug form asks for `errors.log`, which is safe to paste.
